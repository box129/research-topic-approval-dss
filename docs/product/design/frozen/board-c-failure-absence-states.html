Board C · failure & absence states

Five absences that must never look alike

Every state below exists today — four in the capture pack, one confirmed in source with its exact current copy. Nothing invented: no loading skeletons, no offline mode, no retry queue, no fallback provider.

The root cause, found by comparing two captures

The provider-failure screen and the validation screen both render the same dashed panel: “Awaiting topic check — Complete the form to view advisory similarity guidance.” On the validation capture that sentence is correct — the form genuinely is incomplete and the check has not run. On the 503 capture it is false, and it sits above the real cause.

So this is not a wording bug in the failure state. It is one generic “no result yet” placeholder serving two incompatible meanings — “you have not finished” and “we could not run”. That is exactly the collapse Board C exists to prevent, and it is why the fix is a state system rather than five pieces of copy.

Rationale · the operating question

Every state answers two questions before it answers anything else: did the intended operation execute, and was a classification produced? Those two bits distinguish all five states, so each state's title states its own answer rather than describing a shared feeling of emptiness.

Hence no shared “nothing found” component. The five treatments differ in shape, not just wording, so they cannot be mistaken for one another at a glance.

Rationale · fault attribution

Only two of the five states involve anything the user could act on: validation (their input) and provider failure (their retry). The other three are properties of the data or the record. A state must never assign fault to the user unless the user genuinely holds it — the single rule that the captured 503 screen breaks.

So validation speaks in the second person and sits on the field. Failure speaks about the service and sits above the result.

Rationale · what stays

Board A's C1 treatment is carried forward unchanged in structure — it is already the semantic reference. All real validation strings, thresholds and counters are preserved verbatim. The existing empty-state titles and filter message are used as written.

No illustrations, no mascots, no oversized headings. State titles sit at 16–17px in the workspace's own type, adjacent to the content they explain.

STATE-SYSTEM RULES

Eight rules

S1 · Semantics — the governing rule

Every state names whether the operation ran and whether a classification was produced. Those two bits identify all five states uniquely, so no two may share a title, a shape or a surface. No generic “nothing found” component may exist — the one that does today is exactly how “you have not finished” leaked into a 503.

S2 · Colour

Absence and evidence: neutral. System failure: amber, as an edge rule only — never a filled tint, so a fault cannot read as a finding. Validation: red on the field, never at page level. Decision colour is untouched and stays out of all five states.

Green never appears. Not on absence, not on guidance, not on “no problems found”. Red never appears merely because a result is unavailable.

One exemption to Board A's R8, stated rather than assumed. Board A froze “nothing below 4.5:1” with no exception. Inactive controls are the exception — a disabled button's label may sit below 4.5:1, because that is how a control reads as unavailable, and WCAG 1.4.3 exempts text that is part of an inactive user-interface component. The condition: the same information must appear adjacent at full contrast. C3's disabled action is the only instance in this board, and it is paired with “Available once the topic reaches 7 words.” at 4.5:1+. A disabled control may never be the sole carrier of its own explanation.

S3 · Iconography

None of these five states carries an icon. Position, an edge rule and a title do the work. Carried from Board A: warning glyphs are reserved for genuine system failure, and if C2 ever gains one it is the only state entitled to it. No illustrations, no mascots, no decorative empty-state art, no glyph-font or emoji icons.

S4 · Copy

Cause first, in three beats: what happened · what it means · what you can do. Never describe an operation that did not occur. Never assign fault to the user unless they hold it. No internal vocabulary in student-facing copy — no provider name, no “semantic analysis”, no status codes; those belong on administrator surfaces. One short title, one paragraph, and a next action only where one genuinely exists.

S5 · Retry & actions

Retry repeats the failed operation; it never resets the workflow. It is a system action, so it rests in ink per Board A, never in approval green. Where the user's own filter caused the absence, reversing it is the primary action (“Clear all filters”). Where nothing is wrong, there is no primary action — C1 and C4a offer onward routes, not remedies.

S6 · State preservation

A recoverable failure is an interruption, not a new page. Entered values, page context and scroll position survive it. The captured 503 screen discards the student's topic and offers only “Check Another Topic” — so the default path destroys their work. Here the destructive path is never the default, and “Temporary browser state only” stays visible so the pre-check's promise is not quietly broken.

S7 · Responsive

The message sits where the content would have been, at both viewports — not centred in a dashed box. At 390: no clipping, no horizontal scroll, all actions ≥44px and stacked rather than wrapped, error text on the field, filter chips wrapping rather than scrolling. An empty state should be shorter than the content it replaces; if it scrolls, it is wrong.

S8 · Scope discipline

Only states evidenced in captures or confirmed in source. Deliberately absent: loading skeletons (no capture shows a loading state), offline mode, retry queues, automatic provider fallback, any lexical or SBERT fallback, and any new workflow state. The nine other confirmed empty states inherit C4's pattern rather than getting bespoke designs.

What Board C does not settle

Both of my over-claims are now withdrawn, not hedged. The empty-corpus cause line is gone: corpus_size 0 reports that nothing was eligible, and an eligibility rule excluding every record yields the same zero as an unloaded repository — the system cannot tell which, so the copy states only eligibility. And C4b's hidden count has moved below a dashed rule as an optional enhancement, because I had inferred its availability from two chips in a screenshot rather than reading the data flow.

The pattern in both mistakes is the same and worth naming: I reached for the most helpful sentence rather than the most defensible one. A cause the system does not know and a count the UI may not hold are both more useful than the honest alternative — which is exactly what makes them tempting, and exactly why an evidence-grade discipline has to apply to my own additions as strictly as to the existing build's claims.

C4 has no pixel baseline. Every captured list is populated, so unlike C1–C3 I could not compare against a rendered current state — only against the source strings and the EmptyStatePanel component I read in the v2 audit. A capture of any empty list would let me verify the geometry claim rather than assert it.
