Board D · repeated records & primitives

Four semantic families that must never share a costume

Boards A, B and C each fixed one surface. Board D states the shared rules that keep those fixes from being undone by the next component someone builds. All example content is captured synthetic data.

Rationale · what actually went wrong

The original defect was never that a colour was ugly. It was that four unrelated meaning-systems were sharing three colours: a machine classification, a workflow state, a human action, and a system condition. Once HIGH and Rejected resolve to identical pixels, no amount of careful copy recovers the distinction.

Boards A–C fixed that on three screens. But the fix is only durable if the primitives carry it — otherwise the next queue, the next badge, the next confirm dialog reintroduces the collision. Board D's job is to make the correct thing the default thing.

The rule D actually enforces

Colour must never imply an academic verdict where none exists. That is the whole rule — narrower than “green means one thing everywhere”, and it is what the evidence actually supports.

So institutional green stays available for ordinary primary product actions — Sign in, Continue, Apply Filters, Refresh Queue — wherever the surrounding state does not give green a false academic meaning. It remains correct for the Approve action and the Approved status, because there green is the verdict.

The exceptions stay scoped, not generalised. Boards A and C made retry, “Run a new check” and “Clear all filters” neutral because those affordances sit inside evidence and recovery surfaces, where product green would contaminate the evidence reading. An earlier draft of this board extrapolated that into a workspace-wide green-to-ink migration; three local exceptions do not license a global change, and the cost — losing green as a primary-action cue everywhere — buys nothing the verdict rule does not already secure.

D1 · D2

Semantic taxonomy — four families, four visual languages

Family A · similarity classification
What the machine measured
Higher similarity Moderate similarity Lower similarity Not classified

Language: one neutral hue, three fill weights, plus a dashed variant for absence. Rank ordinals, never icons. API token HIGH/MEDIUM/LOW kept as a subordinate mono chip.

Never: green, amber or red. Frozen from Board A.

Family B · workflow status
Where a real record stands
Pending review Approved Revision requested Rejected

Language: pill shape — fully rounded, tinted, 13.5px. Decision semantics are legitimate here because a human produced the state. Pending is neutral blue, not amber: waiting is not a warning.

The shape carries the family. Pill = workflow, 5px radius = classification. Distinguishable in greyscale.

Family C · system state
What the software could or could not do
Check could not run
Service failure
No records
Absence — neutral
Too short: 4 words (minimum 7)
Validation — on the field only

Language: not a badge at all — an edge rule plus a title, or inline field text. Amber for genuine failure, neutral for absence, red only on a field.

Never a pill. Frozen from Board C.

Family D · actions
What a person can do
Approve Request Revision Reject Open Review · Apply Filters Try the check again

Language: 6px radius, ≥40px desktop / 44px touch. Green is legitimate for Approve and for ordinary primary product actions alike — the two are told apart by label, context and the confirmation they trigger, not by hue.

Filled ink is the scoped exception: primary actions inside similarity-evidence and failure-recovery surfaces, where product green would contaminate the evidence semantics — retry, “Run a new check”, “Clear all filters”. Elsewhere ink is simply a secondary weight, not a requirement.

Focus always follows the global gold focus ring, unweakened, including inside evidence.

The rule that makes the taxonomy enforceable

Shape identifies the family before colour identifies the value. A 5px-radius chip is always a classification. A fully-rounded pill is always a workflow status. An edge rule is always a system condition. A 6px-radius filled or outlined control is always an action. That is why the taxonomy holds up in greyscale, for colour-blind readers, and — most importantly — for the next developer, who can tell from the component's shape whether they are allowed to pass it a green.

Corollary: there is no universal StatusBadge. A component whose colour meaning depends on which route rendered it is the defect, not the solution.

D4 · what is shared and what is not

Shared: the hierarchy (primary identity → status/classification → labelled context → metadata → action, in that order), the type roles, the 13.5px metadata floor, unbolded labels, one 600-weight run per record, 10px outer radius, #e5e7eb borders, no inner borders, and the 390px transformation rule.

Not shared — and this is the point of D8: a workflow record has a lifecycle, an owner and an action; an evidence record has a rank, a classification and no action at all. Making them one component would force either an action onto evidence or a rank onto a submission. They share a grammar, not a template.

Route-specific content stays route-specific. Topic Repository needs lifecycle bucket, embedding status and import warnings; Pending Reviews needs student identity and category; My Submissions needs the lecturer's feedback. The primitive fixes how fields are typeset and ordered, never which fields a route shows.

D9

Implementation guidance

categories, not component merges — I have not read enough source to prescribe architecture
Must share semantics

These must agree on meaning wherever they appear, whatever their file layout.

Similarity classification — every render, in every role's view, from one neutral scale.
Workflow status — one status→appearance map for Pending / Approved / Revision requested / Rejected / Under review.
Decision actions — the Approve / Request Revision / Reject triad, including its confirm dialog and the per-action rationale contract.
Colour roles — the D7 table. Every colour use names a role.

Highest leverage: RiskBadge, StatusBadge and the three risk tokens govern every instance in the product — the same two-file change the v2 audit ranked first.

May share presentation

Consolidation would reduce drift, but each is safe to unify only if the shared version stays configurable.

Structured record card — Topic Repository's desktop card with its internal column grid, and the stacked 390px reflow of that same card; field selection stays per route.
Table shell + row typography — header, density, rules, alignment, for routes that are genuinely tables; columns stay per route.
Confirmation dialog shell — one anatomy, semantics passed in.
Duplicate primitive pairs — EmptyState/EmptyStatePanel, LoadingState/LoadingStatePanel, StatCard/MetricCard, AlertBanner/InfoCallout — four concepts, eight files.
Dead files — Sidebar.jsx and Topbar.jsx are unreferenced and carry a forked palette plus glassmorphism.
Must remain distinct

Unifying these would recreate the original defect.

Classification chip vs status pill. No universal StatusBadge whose colour meaning depends on the route.
Evidence record vs workflow record. One has rank and no action; the other has lifecycle and an action.
Decision action vs product action. Both may be green; they must not share a component, because a decision action carries a confirmation dialog, a rationale contract and an irreversible outcome that a Refresh button must never inherit.
The five absence states. Board C's whole point: one generic “no result” component is what let “complete the form” answer a 503.
Validation vs system failure. Field-local red, never a page-level failure treatment.
What Board D standardises

Shape as family identifier — chip, pill, edge rule, control — so the four meaning-systems cannot collapse again. One colour rule: never imply an academic verdict where none exists, which keeps green available for ordinary primary actions and scopes the neutral-affordance exception to evidence and recovery surfaces. One confirmation anatomy whose confirm button inherits the action's semantics, with the grammar fixed. Two record primitives sharing a grammar — hierarchy, type roles, spacing, radii, borders, action placement, 390px transformation. Nine named text roles with a 13px task-essential floor and 11–12.5px reserved for nonessential labels. Nine colour roles with explicit allowed and prohibited contexts, and gold reduced to focus alone.

What deliberately remains different

Green for ordinary primary actions — deliberately left in place across the workspace, with neutrality required only inside evidence and recovery surfaces. Which fields each route shows — Topic Repository's lifecycle bucket and embedding status, Pending Reviews' student identity, My Submissions' lecturer feedback. The presence or absence of a row action. Rank ordinals, which belong only to machine-ordered evidence. Sort and filter controls, which belong only to workflow lists. Review Detail's inverted hierarchy on a decided record, frozen in Board B. And the five absence treatments, which stay five.

Also unchanged by design: workspace density, the three named widths, navigation, dashboards, and forms. Board D adds no new screen.

Implementation questions needing source or data confirmation

1 · Is Under review a topic-repository lifecycle bucket or a submission status? Blocking its final token. Shown provisionally neutral with a dashed pill border rather than resolved visually. If it is a submission status it joins Family B and takes the Pending treatment; if it is a repository lifecycle bucket it stays neutral. Either way it is not red and not green.

2 · How many distinct workflow statuses exist? I have seen four rendered plus AWAITING_REVISION in source. If there are others — withdrawn, superseded, resubmitted — each needs a role assignment before the pill map is fixed.

3 · Does any evidence surface currently offer a row-level action? D8 asserts evidence records have none. If a route lets a lecturer open or cite a related topic, that is a legitimate exception and the primitive needs a defined action slot rather than a prohibition.

4 · Which surfaces put green close enough to a classification to read as a verdict? The global green-to-ink migration is withdrawn, so this is now a targeted question: an inventory of primary buttons that sit within an evidence or absence surface, where the scoped neutral rule applies. Sign-in is separately worth checking — its submit forces gold via three !important overrides, which no role in the D7 table sanctions.

5 · Are StatCard and MetricCard genuinely one concept? Source showed one as a pass-through to the other, which suggests yes — but I read them in the v2 audit only, and a merge should be confirmed against every call site rather than that inference.

6 · Deliberately out of scope here: the F-1 similarity-scale contract, F-2 duplicate snapshots, F-3 the 4-vs-5 count and F-4 directive stored copy. All four are functional or data defects; none is addressed visually anywhere in Boards A–D.
